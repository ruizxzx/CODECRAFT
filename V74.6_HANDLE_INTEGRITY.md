# OFFSCRPT V74.6 — Handle Integrity Fix

## Problem fixed
Google display names were being automatically reserved as public @handles. This made a new user see their own display name reported as "Handle taken" and caused unclaimed users to appear in people/creator surfaces with a username.

## Changes
- New community profiles start with `username: ""` and no `usernames/{handle}` document.
- The claim modal no longer pre-fills ordinary users' Google display name as a handle.
- Existing unclaimed profiles can claim a handle through the existing claim modal; the claim is atomic with the profile update.
- Unique handle changes are supported from **Settings → Profile → Identity** and from **Edit Profile** on a user's own community profile.
- Handle availability is checked against the cloud username registry; final uniqueness is enforced by an atomic Firestore transaction.
- Users can clear a handle; the previous reservation is released atomically.
- Username registry rules now prevent a signed-in user from creating arbitrary extra reservations; a reservation can only be created/released as part of the corresponding profile transaction.
- People/creator discovery already filters to profiles with a claimed handle.
- Identity propagation uses the newly selected handle so legacy author snapshots do not retain the previous handle after a change.

## Manual test cases
1. Sign in with a new test Google account. The display name must not reserve its normalized name as a username.
2. In the handle claim modal, enter the display name: it must show TAKEN only if a real `usernames/{handle}` document exists; it must not be pre-reserved by the new account.
3. Cancel the modal. Open Settings → Profile → Identity and claim a different unique handle.
4. Confirm Firestore has `users/{uid}.username == <handle>` and `usernames/<handle>.uid == <uid>`.
5. Change the handle again. Confirm the new reservation exists and the old `usernames/<old>` document is gone.
6. Search People. Accounts with no handle must not appear.
7. Open the public profile from another account and confirm the new handle is shown from the cloud profile subscription.
8. Try to claim a handle already reserved by another account. The UI must report taken and the Firestore transaction must reject the write.
