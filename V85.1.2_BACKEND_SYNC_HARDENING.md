# OFFSCRPT V85.1.2 — Backend Sync & Runtime Hardening

V85.1.2 hardens V85.1.1 without introducing unrelated features. It removes browser-side CommonJS runtime usage, completes community invitation/join-request authorization, strengthens Vault ownership/reference checks, adds collaborator subcollection authorization, and keeps scheduled publishing on GitHub Actions (5-minute cadence).

## Security-critical changes
- Community invitations use deterministic recipient-scoped IDs and explicit recipient/manager state transitions.
- Accepted invite and approved join-request membership creation are coupled through Firestore transaction state (`getAfter`).
- Community Wiki, FAQ, and resource writes are role-gated; resources require HTTP(S) URLs.
- Vault collections/items are owner-scoped and item references are validated against the same user.
- Creator collaborators have Firestore-backed roles and explicit publish permission; editor content writes cannot change ownership/publication/collaboration fields.
- Scheduler accepts only the configured `CRON_SECRET`, handles malformed secrets safely, processes scheduled publication and unpublish states, and marks failed transitions as `failed`.

## Scheduler requirements
Set these in Vercel/server environment only: `GOOGLE_CLOUD_PROJECT`, `GOOGLE_SERVICE_ACCOUNT_CLIENT_EMAIL`, `GOOGLE_SERVICE_ACCOUNT_PRIVATE_KEY`, and `CRON_SECRET`. GitHub Actions needs `CRON_SECRET` and the public production URL variable. Never commit the service-account private key.

## Firebase deployment note
`firestore.rules` and `firestore.indexes.json` in the release are source-of-truth artifacts. They must be deployed to the actual Firebase project; repository presence alone does not make production rules/indexes active.

## Known limitations / environment-dependent verification
Cross-account Firestore emulator tests and live scheduler execution require valid Firebase credentials/project access. These are reported as BLOCKED when unavailable rather than being represented as passing tests. External semantic/vector provider freshness depends on configured provider infrastructure.

## V85.1.2.1 reaction + handle hardening
- Community invitations accept a public @handle and resolve it to the Firebase UID internally through the canonical `usernames/{handle}` reservation.
- Community invitation UI no longer asks users for a Firebase UID.
- Community post votes resolve the actual post location before reading/writing the vote state; this fixes vote state persistence for nested community posts.
- Community reposts now have explicit nested Firestore authorization and atomic bookkeeping, so repost count and user profile repost state persist together.
- Reaction counters are restricted to authenticated, non-restricted users and one-step counter transitions.
