# V75.12 — Firestore Quota / Usage Optimization

## Observed high-cost paths audited
- Repeated `users/{uid}` profile reads across App, community, social, article and preference surfaces.
- Recommendation signal subscriptions maintaining eight independent listeners plus a delayed duplicate fallback fetch.
- Per-series follower membership checks issuing up to 100 `getDoc` calls for one personalized-home load.
- Hero reader count `getCountFromServer` running on every Hero mount.
- Master Control platform counts and article analytics being fetched repeatedly when the admin dashboard is opened.
- Public profile directory enrichment performing N+1 username reservation reads.
- Admin author/profile synchronization running on authentication refresh.
- Notification preference reads repeated for notification fan-out.

## Protections introduced
1. Short-lived memory cache for hot documents, query results and count queries.
2. In-flight request deduplication so simultaneous callers share one Firestore request.
3. Quota cooldown: `resource-exhausted`/429 errors are not retried and duplicate reads are temporarily suppressed.
4. Stale-cache fallback for selected read-only identity/config surfaces during quota exhaustion.
5. Recommendation listeners reduced to high-value realtime signals; search and reaction indexes refresh on a 2-minute cadence.
6. Removed the old delayed 900ms recommendation fallback that duplicated the initial eight listener reads.
7. Series follow state uses one bounded collection-group query instead of one read per series.
8. Platform count/analytics reads are cached for short windows.
9. Admin author synchronization is throttled per auth session.
10. Profile caches are invalidated after successful profile writes.

## Important limits
Caching cannot create Firestore quota. A project that has already exhausted its daily allocation still needs the quota window to reset (or a billing-plan change) before previously uncached reads/writes can succeed.
